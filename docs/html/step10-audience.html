Audience Resolution

Turning a section heading into a test a computer can run — and matching it against every audience the system already knows, without ever guessing.

01 First: this is not the next link in the chain

This is almost certainly why Step 10 felt disconnected. The numbering implies it follows Step 9. It doesn't.

Steps 1 → 9 are a single chain: each one eats what the last one produced. Step 10 branches off the clause tree instead, runs beside window building, and doesn't rejoin until filing.

Where step 10 actually sits

                RESOLUTION                                    streams

Two consequences worth holding on to:

  • It reads the clause tree, not the windows. It only looks at headings — the containers Step 8 marked as junk. It never touches clause bodies.
  • Drafting does not wait for it. A window carries its audience as wording inside the heading trail, which is all the AI needs. The formally resolved audience is only needed later, when a rule is filed.
Why it exists at all

Without this step, a rule extracted from the QSB chapter and a rule extracted from the non-QSB chapter are indistinguishable once stored. Six months later SEBI amends the QSB one — and the system cannot tell which of the two to change. It either rewrites the wrong rule, or decides one supersedes the other and deletes an obligation that thousands of firms still owe.

The vocabulary is a dropdown, not a text box

The obvious objection to translating headings into tests: what stops the AI writing is_qsb = yes in one circular and qsb = applicable in another?

Mostly this does. The AI is handed a list of firm properties and told to pick from it rather than invent names. But it is never handed the whole list — that would work at 30 properties and fail badly at 300.

What actually goes into the prompt
STABLE CORE  ~25 properties · identical every call · prompt-cached

    category              stock_broker | investment_adviser | ...
    is_qsb                yes / no
    holds_client_funds    yes / no
    is_clearing_member    yes / no
    active_clients        a number
    ...

RETRIEVED TAIL  ~10 properties · chosen for THIS heading

    heading: "Obligations of brokers offering algorithmic trading"
                          ↓ retrieve by meaning
    offers_algo_trading         yes / no
    uses_colocation             yes / no
    has_approved_algo_strategy  yes / no

PERMISSION  "if none of these fit, propose a new property"

                          ────────────
                          ~35 options, not 300

Cost is the smaller reason. Sending everything would be expensive, but a stable prefix is prompt-cached and the price largely disappears. Accuracy is the real reason — a model choosing from 300 options performs measurably worse than one choosing from 35, because entries buried mid-list get less attention. A bloated vocabulary makes the translation worse, not merely pricier.

How big does this list actually get?

What it isRough size
Data-points facts a firm reports — audit dates, net worth, client counts thousands
Firm properties characteristics that decide who a rule applies to tens

Firm properties exist only to slice the population — registration type, a handful of activity flags, a few size thresholds. Regulation doesn't actually divide firms hundreds of ways, so this set stays small while the data-point register grows into the thousands.

The governance rule that keeps it small

A property earns its place only when some rule's audience depends on it. "Net worth ≥ ₹5 crore" is a rule about a data-point — that doesn't make net worth a firm property. It becomes one only if a circular says "brokers with net worth above X shall…", using it to define who is being addressed.

If the vocabulary starts heading for the hundreds, that's the signal data-points are leaking in where they don't belong.

What if retrieval misses?

Then the AI proposes a new property that duplicates one already in the register. That fails safely, because a proposal doesn't go straight in — it runs through the same ladder as everything else: normalise, exact match, implication, similarity, judge. Worst case a human sees "proposed: offers_algorithmic_trading — looks like existing: offers_algo_trading" and rejects it.

A retrieval miss costs one rejected proposal, not a corrupted vocabulary.

03 The idea the whole step rests on

Everywhere else in this pipeline, matching is done by meaning similarity. Two data-points are the same thing if their descriptions land close together in vector space. That's the right tool there, because "date of last audit" is a human notion with fuzzy edges.

An audience is different. An audience is a set of firms. Sets can be compared exactly. Using a similarity score would be discarding certainty we could have had for free.

The rule

The AI translates the heading into a test. From that point on, the computer decides — not the AI.

Names vs tests — the same two headings, two approaches
MATCHING BY NAME                            MATCHING BY TEST

"Obligations of Qualified Stock Brokers"    → category=stock_broker AND is_qsb=true
"QSB Obligations"                           → category=stock_broker AND is_qsb=true

     ↓                                           ↓
different words, different numbering,       character-for-character identical
different depth in the document
     ↓                                           ↓
guess whether they're the same              know they're the same

It's the same trick as matching "senior citizens" to "old people". Comparing the words is guesswork. But if both are written as age > 60, you just look at them and know.

05 Why a new audience needs a human

This is the one deliberate interruption in the entire pipeline, and it buys a hard guarantee.

A wrongly created audience produces the duplicate branch problem: two separate QSB nodes, rules scattered across both, and a firm seeing half its obligations with no indication the other half exists. Nothing downstream can detect it, because both branches look perfectly valid.

Because new audiences are rare, one approval click prevents it outright. And crucially the gate doesn't block the expensive work — clauses under a pending audience are still parsed and still drafted. Only the final filing waits.

On a cold start

Loading 1,000 circulars into an empty system would mean an approval prompt on practically every document. So bulk load doesn't decide as it goes: it collects every audience candidate across all 1,000 documents first, normalises them, and lets the exact and implication rungs collapse the duplicates. Thousands of headings reduce to roughly 40 distinct audiences, approved in one sitting.

06 Audiences form a lattice, not a tree

A folder structure gives everything exactly one parent. Real regulation doesn't work that way — "QSBs holding client funds" sits beneath both "QSBs" and "firms holding client funds", and inherits obligations from both.

The stamped audience is the payload. When Step 12 files a rule, its fingerprint is built from audience + data-points + the shape of the check. Because the audience is baked in, the 180-day QSB rule and the 90-day non-QSB rule produce different fingerprints and can never be mistaken for versions of each other.

08 Where it breaks

Telling who from what

"Obligations of QSBs"                             → WHO
"Cyber security"                                  → topic
"Algorithmic trading"                             → topic
"Brokers offering algorithmic trading to clients" → WHO  ← nearly the same words

Get it wrong one way and you create a phantom audience — the approval gate catches that. Get it wrong the other way and rules pile into an audience that's too broad, so firms receive obligations that aren't theirs. That direction has no automatic guard, and would surface as a firm querying a rule they shouldn't have.

Audiences written in prose

"Where the broker holds client funds, the audit shall…" is a genuine audience buried mid-sentence. This step never sees it, because it only reads headings. It survives as a condition attached to that single rule — correct, but that firm's dashboard won't group it the way a real audience would.

Table rows partly close this gap, since a rule table's first column is very often the audience. Prose remains open.

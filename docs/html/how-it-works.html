Setu · SEBI Compliance Portal

How the whole thing works

SEBI publishes rules as prose in 400-page PDFs. Every firm reads them itself, and interprets them differently. This turns those documents into one live rule graph — so a firm sees exactly which rules apply to it, and whether it's compliant right now.

⚠ Measured — read before the steps

Every number here was produced by running the real parser over 8 real documents · ~1,700 pages · 2 regulators — not estimated. Three designs were discarded because of what the measurements showed.

The biggest finding: there are three ways a document says who a rule applies to, and they stack. 

PATTERN C  document-level declaration   "this applies to: X, Y, Z"
             every document has one · works in SEBI AND RBI
   ↓
PATTERN A  chapter scoping             a heading narrows it      4 of 8
   ↓
PATTERN B  taxonomy + thresholds       tiers with per-type limits 1 of 8

Step 10 was designed for A only. Pattern C — the floor under everything — was missed entirely, and it's the one that matters most.

Why this matters more than anything else here

Without the split, every improvement to the hard logic means re-running the AI over two million clauses. With it, you can iterate on the difficult part fifty times a day for nothing.

The seventeen steps

01Receive and checkbuilt

Is this a real file, from someone allowed to send it?

IN raw bytes + dates + login→OUT a validated package
  • Peek at the first 5 bytes — a real PDF always starts %PDF. Catches a renamed Word file instantly, without reading the rest.
  • Filename becomes a clean permanent handle: Master Circular 2024.pdf → master-circular-2024.
  • The typed dates become real dates. The effective date is what orders everything later.
  • Any check fails → nothing is saved anywhere, so there's no half-record to clean up.

Not one word of the document has been read yet.

02Fingerprint and dedupebuilt

Have we already processed this exact file?

IN validated package→OUT + fingerprint + verdict
hash the whole file → one short code
   identical files      → identical code
   one character changed → completely different code

   match + job COMPLETED        → skip, we're done
   match + job failed/half-done → redo it
   same content, new name       → ask a human
  • Skip on "job completed", never on "file present." A crash at document 500 leaves its file stored but half-processed — skipping on presence would silently lose it.
  • That one distinction is what makes a 1,000-document load resumable.
Where it breaks

A re-scanned or re-exported PDF has different bytes, so it passes as new. That's fine — it's caught later at clause level, where identical text reuses all the cached AI work anyway.

03Store the filebuilt

Put the PDF somewhere permanent and carry a ticket instead.

IN 40 MB of bytes→OUT a short locker number
  • Goes to a file store, not the main database — big opaque blobs and searchable records are different jobs.
  • Every downstream step now carries a light ticket. The 40 MB is only pulled back when someone actually needs the pages.
  • Written once, never modified, never deleted — even if the parsing later turns out wrong. This is the evidence every rule must trace back to.
04Create the job recordbuilt

Open a control desk, then hand the work to the background.

IN the ticket→OUT job id + live progress channel
  • One row holds status, a diary that every later step writes into, and an error slot.
  • A 419-page circular takes minutes; a thousand takes days. So the browser gets a ticket number, not a spinner.
  • This record is what Step 2 reads to answer "is this genuinely done?" — without it the system has no memory of its own progress.
05Read the document — two lanespartly built

Turn a printing format back into readable text — without mangling the tables.

IN the PDF→OUT ~16,000 prose lines + table grids
The thing that surprises everyone

A PDF contains no sentences, paragraphs or even lines. It's a printing instruction sheet — thousands of fragments saying "put these characters at position 72 across, 340 down." A line only looks like a line because several fragments sit at the same height. 

5a  FIND THE TABLES FIRST   ← must be first
    otherwise table cells flatten into the prose and
    "Stock broker | ₹1 crore | 31 Mar" becomes one nonsense line

5b  EXTRACT PROSE LINES      skipping the table regions
    keeping: page · font size · bold · indentation

5c  EXTRACT TABLES AS GRIDS  rows, columns and the header row
    kept separately — a cell means nothing without its header
  • Font size and indentation are kept because they're a second, independent clue to structure. Throw them away and you're guessing headings from numbering alone.
  • Tables often hold the densest rules — a three-column table of category / net worth / deadline is three complete obligations per row.
Where it breaks
  • Scanned PDFs have no text at all, just an image. The job stops with a clear reason and needs an OCR path — which matters, since older circulars are more likely to be scans.
  • Merged cells and multi-row headers still degrade.
06Build the clause treebuilt

Recover the document's outline, which the PDF threw away.

IN 16,240 flat lines→OUT 2,493 nested clauses
One question per line: does it START a clause, or CONTINUE one?

"9. Obligations of Qualified Stock Brokers"    → depth 1, new
"9.5 Cyber security"                           → depth 2, parent = 9
"9.5.3 Audit requirements"                     → depth 3, parent = 9.5
"9.5.3.1 A cyber security audit shall be"      → depth 4, parent = 9.5.3
"carried out at least once every 180 days."    → no number → glued onto 9.5.3.1
"9.5.3.2 A broker unable to comply shall"      → depth 4, sibling
  • Depth = number of dots. Parent = the nearest earlier clause with a smaller depth.
  • Expectation beats pattern matching. "1.5 times the net worth" starts with a number but isn't a clause. If the last clause was 9.5.2, then 9.5.3 is expected and 1.5 isn't — which kills most false positives.
  • Font separates a heading (short, bold, no verb) from an obligation (long, normal weight, "shall").
⚠ Portability limit — this grammar is SEBI-specific

Numbering styles found in an RBI Master Direction:

inline decimal  "9.5.3.1 A cyber audit shall…"    0   ← what this step expects
bare number alone on its own line                37
Chapter – I / Chapter – II                       20
lettered  (a) (b)                                 8
roman lower  i. ii.                               4
roman upper alone  I. II.                         2

Zero. RBI puts the number on its own line and the heading on the next:

Chapter – I
Preliminary
1.                              ← number alone
Short title and Commencement    ← heading on the NEXT line
(a) These Directions shall be called…

Result: 31 pages → 38 clauses, against SEBI's ~6 per page. The tree comes out structurally wrong, so nothing downstream can be trusted for that document.

This is a documented boundary, not a task. While Setu is SEBI-only, this step is fine. Extending to RBI / IRDAI / PFRDA needs a pluggable numbering grammar per regulator — a new component, not a tweak.

⚠ Two structural facts the design assumed away

1 — Some circulars are bilingual.

7.1  "बाजार की बुनियादी संस्थाएँ (एमआईआई)"        ← Devanagari
7.1  "Market Infrastructure Institutions (MIIs)"  ← English, same number

79 of 1,082 clauses (7.3%) are Devanagari

Two interleaved trees, every number appearing twice. Needs a language pass before segmentation — otherwise the numbering audit reads the second copy as duplicates rather than gaps, and every citation has two candidate targets.

2 — The clause number is not a unique key, even in monolingual documents.

master circular   144 duplicated numbers   "1" appears 76× · "2" appears 83×
CSCRF              81 duplicated numbers   "1" appears 153×

Sub-lists restart numbering in every section. Full dotted paths like 9.5.3.1 are far more unique, but a citation to a bare "para 1" can't be resolved without context — which Step 12's modifier resolution depends on.

07Check the tree for holesbuilt

Find clauses we lost — because a lost clause is completely invisible.

IN the tree→OUT repaired tree + a report
Why this step exists

A wrongly extracted rule gets noticed eventually. A clause that never entered the tree produces no error, no warning, no gap on screen — the obligation simply isn't there, and nobody finds out until a regulator asks. 

Under 9.5:  9.5.1, 9.5.2, ____, 9.5.4      ← where is 9.5.3?

Lane 1  glued to the text?     "9.5.3The broker shall..."
                                  → split the line, rebuild · no AI

Lane 2  cited mid-sentence?   "in accordance with para 9.5.3"
                                  → a reference, not a clause · cleared

Lane 3  found nowhere?        → genuinely missing → FLAG
  • If Lane 1 repairs anything, the tree is rebuilt and re-audited — an un-glued clause may have swallowed children of its own.
  • Measured: 1,603 numbers checked on the master circular → 4 genuine gaps flagged, 0 false repairs. The four were verified by hand as real.
  • Annexures are excluded — their numbering is chaotic and once produced 23 false alarms.
08Decide what reaches the AIbuilt

Skip only what is provably not a rule. Send everything else.

IN 2,493 clauses→OUT 2,193 sent · 300 skipped
ALLOWLIST  "only send things that look like obligations"   ✗ we tried this
BLOCKLIST  "send everything except provable junk"          ✓ correct

what the allowlist silently dropped:
   "1.1 the total number of active clients of the stock broker"
   no "shall", short — yet it's one of four parameters that decide
   whether a broker is a QSB at all

           QSB circular     11 of 39  →  37 sent
           master circular  1,231     →  2,193 sent
The whole argument in one line

Sending too much is a bill. Sending too little is an obligation that vanishes with no error, no gap and no symptom. Those costs are not symmetric.

  • Junk = table of contents · bare headings · under 15 characters · letterhead. That's all.
  • Junk means "don't send", never "discard." A junk heading is simultaneously the most important node in the document, because it tells us the audience for every clause beneath it.
⚠ Measured bug — the length rule deletes audience definitions 
on the 205-page multi-entity circular:

  7.2  "Qualified Res"    13 chars  →  junk  ✗ dropped
  7.3  "Mid-size REs"     12 chars  →  junk  ✗ dropped
  7.4  "Small-size REs"   14 chars  →  junk  ✗ dropped

Those three clauses define who the entire framework applies to. An audience name is short by nature, so a length threshold is actively hostile to the content that matters most.

Fix: never junk a short clause when its parent's lead-in announces a list — "…the following five categories". A short list item is normal.

09Build the windowspartly built

Carry exactly the context that makes a clause mean something — and nothing more.

IN tree + tables→OUT ~2,370 self-contained blocks
A clause alone is often meaningless:
   9.5.3.2  "The report shall be submitted within 15 days."
            what report? by whom? to whom?

A WINDOW
  ┌─ CONTEXT ────── the heading trail        always
  ├─ LEAD-IN ────── the parent's own text    when it exists
  ├─ CLAUSE ─────── the clause itself
  ├─ REFERENCED ─── other clauses' text      only some kinds
  └─ SIBLING ────── the previous clause      ~1% of clauses only

Why the lead-in isn't optional

1.   Based on the following parameters, stock brokers shall be
     designated as Qualified Stock Brokers:
1.4     the end of day margin obligations of the broker

read 1.4 alone → a noun phrase. No verb, no duty, unusable.
the obligation lives one level up
  • The whole window is fingerprinted, not just the clause. The same sentence under "Obligations of QSBs" and "Obligations of non-QSBs" means different things — hashing the clause alone would reuse an answer from the wrong context.
  • The sibling is pulled in only on unambiguous signals — no subject at all, or "such" / "the said", or a real pronoun. Deliberately not the broad "the + noun" pattern. See below.
This one was designed twice, and measurement killed both versions

First design: trigger on any definite backward reference ("The audit shall…"). Second: give up on detection and always include the previous sibling's first sentence. Before building either, the detector was run over the real 419-page circular. 

2,183 non-junk clauses

 72.1%  don't start with an article at all
 17.4%  definite ("the ...")
  1.0%  pronoun
  0.7%  strong backward reference ("such", "the said")
  0.0%  no subject at all   — one clause in the entire document

of the candidates:
 10.7%  excluded entity noun    "the broker", "the Board"
  3.2%  antecedent in the PARENT   ← the lead-in already covers these
  2.8%  antecedent in the SIBLING  ← what the fix would buy

And the examples showed even 2.8% was inflated:

18.4.1.2  "the available total assets of clients with the stock broker;"
     1.2  "the available total assets of clients with the stock broker;"
          → list fragments, not backward references
          they need the PARENT's lead-in, already carried

     2.2  "It is recommended that resources employed shall have..."
    17.1  "It has been decided to put in place an Early Warning..."
          → dummy "it" — grammatically refers to nothing

     1.8  "The system auditors should follow the reporting standard..."
    12.1  "The transferee shall obtain fresh registration from SEBI..."
          → entity nouns missing from the exclusion list

About one in four of the strongest-category examples was genuine — so the real rate is 1–3% of clauses. That makes the broad heuristic imprecise, and makes always-sending a bad trade: +23% tokens on every window to fix ~2%.

So: trigger on the unambiguous signals only (~1% of clauses, negligible cost), and let Step 11's inferred field catch the rest — the model knows when it's confused, and a regex never will.

The measurement took twenty minutes and discarded two designs, one of which had already been argued for twice.

10Work out who each section applies todesigned · branch

Turn a heading into a test — then let the computer decide, not the AI.

IN title + first clauses + headings→OUT every clause stamped with its audience
🆕 10a — read the document's base applicability first (Pattern C) 
SEBI Cloud Framework, p2:
  "The framework shall be applicable to the following REs:
     i. Stock Exchanges   ii. Clearing Corporations
     iii. Depositories    iv. Stock Brokers through Exchanges …"

RBI IT Outsourcing, p6, under a heading titled "Applicability":
  "(a) These Directions shall be applicable to the following entities,
       collectively referred to as 'regulated entities' or 'REs': …"

One AI call per document, stamping every clause with a floor. It's the only pattern that works across both regulators — and the Cloud framework has one heading in 53 pages, so without it that document yields zero audiences.

Master circulars state applicability in the title — "Master Circular for Stock Brokers" — which Step 8 currently junks as letterhead. That has to be preserved and passed here. 

MATCHING BY NAME                        MATCHING BY TEST

"Obligations of Qualified Stock Brokers"   → category=stock_broker AND is_qsb=true
"QSB Obligations"                          → category=stock_broker AND is_qsb=true

different words, numbering and depth       character-for-character identical
         ↓                                            ↓
guess whether they're the same             know they're the same

Same trick as matching "senior citizens" to "old people". Comparing words is guesswork; if both are written age > 60, you just look and know.

THE LADDER — stops at the first rung that resolves it

0  cheap gate — REMOVED after measurement (see below)
                      every heading now gets a call · 148 out of ~2,400
   was: does the wording look like an audience?
                      no → inherit the parent's · no AI call · ~85% exit here
1  translate          one AI call → a name and a test
2  normalise          sort terms, one form per value
3  exact match        identical test → provably the same → REUSE
4  implication        every firm matching A also matches B?
                      → A is NARROWER → nest it underneath
5  similarity         no logical match → compare descriptions by meaning
6  AI judge           borderline candidates only
7  new audience       → ⚠ HUMAN APPROVAL
⚠ The gate was measured, scored zero, and deleted 
master circular (419p, 148 headings)   phrase gate → 0
CSCRF           (205p,  64 headings)   phrase gate → 0

The phrase list ("obligations of", "applicable to"…) was written against an invented example — "9. Obligations of Qualified Stock Brokers" — which appears nowhere in the corpus. Real headings read: 

"18.5  Enhanced obligations and responsibilities for QSBs:"
"52    Conditions to be met by Broker for providing Internet Based Trading"
"1.8   BCP/DR (Only applicable for Stock Brokers having BCP/DR site)"

And the asymmetry ran the wrong way. A false positive costs one wasted call answering "no, it's a topic". A false negative means a section silently inherits the wrong audience, and every rule beneath it is filed under the wrong group. The gate saved 6% of calls while risking exactly that.

  • The AI translates. It never matches. It's never shown the existing register — showing it and asking "is this one of these?" would put the decision back in the model's hands.
  • A new audience needs a human click. It's the one deliberate interruption, and it prevents the failure nothing downstream can detect: two separate QSB branches with rules scattered across both.
  • The gate never blocks the expensive work — clauses under a pending audience are still parsed and drafted. Only filing waits.
Where it breaks
  • ⚠ Pattern B (1 of 8 documents) — deferred. In CSCRF the audiences are a numbered list, not headings (kind=clause, leaf=true, no heading), and their thresholds sit in a separate table per intermediary type — so "Mid-size RE" is a matrix, not a category. When built, model it as a derived property in the Formula Register (re_category computed from AUM/clients/turnover), so the audience test collapses to re_category = mid_size and the tier is computed rather than self-declared.
  • Telling who from what. "Algorithmic trading" is a topic; "Brokers offering algorithmic trading" is a group of firms. Nearly the same words, opposite classification. This is also why an entity-noun filter wouldn't work — "Cyber Security framework for Stock Brokers" contains an entity noun and is still a topic.
  • A section that steps OUT of its parent — "9.9 Provisions applicable to all brokers" sitting inside a QSB chapter. Composing blindly would file it as QSB-only, so ~90% of brokers never learn of a rule they owe. Fixed by checking the AI's claim with logic, and stopping for a human only when the child is genuinely broader.
  • Audiences written in prose rather than headings — handled later by promoting the rule's precondition through this same ladder.
11Draft the rulespartly built

The AI finally reads a clause — one at a time, in isolation, in parallel.

IN ~2,370 windows→OUT rules · definitions · modifiers · declines
THE CACHE COMES FIRST
   look up (window hash + prompt version)
     found     → use it. no call, no cost.
     not found → queue for extraction

   master circulars restate earlier ones VERBATIM
   → on a bulk load ~40% of windows are exact repeats
   → each unique window goes to the AI once, ever
Why reuse is safe

The cache stores what the AI said about one clause in isolation — never a finished rule. A clause always means what it means; what changes between circulars is the surrounding clauses, which are combined later in the free layer. Same cached translation, correctly different final rules. 

FIVE POSSIBLE ANSWERS

1  rules        one clause often holds several duties
                 "audit every 180 days" AND "report to the board" = 2 rules

2  definition   "net worth means capital + reserves − losses"
                 → a FORMULA, not a rule. The form asks for the 3 inputs
                   and computes the total — so it can't be fudged.

3  precondition "where the broker holds client funds..."
                 → kept structured, so it can become a real audience

4  modifier     "9.5.1 applies only when customers > 5,000"
                 → creates NO duty of its own · it changes another rule

5  nothing      procedural text, or duties addressed to SEBI itself
                 → declining is a legitimate answer

Three validation lanes — deterministic first, always

1  TYPE CHECK       date vs date  ✓     date vs rupees  ✗ reject
                    every number must carry a unit

2  MODIFIER CHECK   the AI says it targets "9.5.3"
                    but the text only ever mentions "9.5.1"  → flag

3  NUMBER FIDELITY  text says 180 · the rule says 90
                    90 appears nowhere → TRIPWIRE
                    → not a rejection — a referral to a verifier,
                      told the SPECIFIC complaint
                    → and any correction must pass the same check
The principle this is the third instance of

Cheap deterministic check → tripwire → targeted AI adjudication with a specific complaint → verify the answer with the same check. The AI is never the first responder, and never the last word.

  • Never converts units. The circular says "half-yearly"; we store "6 months", not "183 days". Six calendar months from 31 Jan is 31 July; 183 days is 2 August — a firm audited on 1 Aug is compliant under one reading and in breach under the other.
  • Fully parallel. Each call is stateless, so document order has zero effect on the output. Order only matters later, in the cheap deterministic steps.
Where it breaks
  • Implied subjects the document never states — "the report shall be submitted" to whom? Output is well-formed, correctly typed, every number present. No deterministic check can catch it. Handled by making the AI declare its guesses in an inferred field → anything non-empty goes to human review.
  • A duty split across non-adjacent clauses, where no wording points backwards.
12Assemblydesigned

The parallel work stops. Everything is walked in order and combined.

IN a pile of disconnected pieces→OUT rules with final applicability
THE TRIGGER IS A PHASE BOUNDARY, NOT AN EVENT

PHASE A — EXTRACTION    all windows, in parallel, any order
                        → every rule and modifier now exists
                        ─────────────────────────────────
                                  ▼
PHASE B — ASSEMBLY      walk them in order and build the graph

nothing waits for anything · no callbacks · no scheduler
RESOLVE · INDEX · APPLY

  the AI gave us  targets: "9.5.1"   ← a STRING, connected to nothing
                       ↓
  resolve to the actual clause         → clause id 88213
                       ↓
  group all modifiers by their target  → 88213 → [restrict: customers > 5,000]
                       ↓
  walk the rules in document order
     a. look up the index  ← the combine
     b. apply
     ...
     f. fingerprint      ← the ordering is guaranteed by the SEQUENCE,
                            not by anyone remembering it
WHAT EACH MODIFIER DOES

restrict   audit within 6 months · all QSBs
           → audit within 6 months · QSBs with >5,000 customers

exempt     daily reporting · all brokers
           → all brokers EXCEPT those with <500 clients

extend     audit · QSBs  →  audit · QSBs OR clearing members

override   doesn't edit the original — creates a sibling
           all brokers keep 180 days · QSBs get a stricter 90-day rule
  • A modifier targeting an older circular becomes an amendment — that rule is already live, so narrowing it goes through diff card → approval → new version. No special machinery needed.
  • An orphaned modifier (target was declined or never parsed) is a second, independent signal that a clause was lost upstream.
Where it breaks
  • "The preceding paragraph" is ambiguous about level — the previous clause in reading order, or the previous one at the same level? Those can mean exempting one requirement versus an entire section. Fixed by listing the candidate neighbours in the window so the AI names one explicitly.
  • A condition using an unknown property — the rule waits in REVIEW rather than being filed unrestricted (over-inclusive, and a future phantom amendment) or dropped (silently missing).
  • A modifier modifying a modifier. Solved by making applicability an expression tree and tagging each change with its source clause — then always flagged, because "the exemption shall not apply to X" is a double negative humans misread too.
13Resolve the data-pointsmostly built

Turn invented words into permanent ids, so one real fact exists once.

IN rules full of free-text tokens→OUT rules pointing at registry ids
The idea

Contacts on a phone. You tap "Mom" and it dials a number. Different people save her as Mother, Amma, Mom — one actual line. The AI invents a label every time it reads a clause: aud_dt, last_audit_date, audit_completion_date. Three labels, one fact. 

THE FUNNEL, PER TOKEN

1  one description line   "name: audit_last_date.
                           meaning: the date the last cyber audit was carried out.
                           topic: cybersecurity_audit"
2  embed it               batched, 128 at a time
3  find the 5 nearest existing data-points by meaning
4  ⛔ TYPE GATE          a date can NEVER merge with a count,
                          however similar the wording
5  same-name tripwire     does any name or alias exactly match?
6  decide                 tripwire hit    → JUDGE (always)
                          < 0.15          → REUSE
                          0.15 – 0.45     → JUDGE
                          > 0.45          → CREATE NEW
7  reuse → record the new spelling as an alias (audit trail only)
   new   → create it and embed it IMMEDIATELY, so the next token finds it

The rule that's easy to get wrong

The audience must NEVER enter the description line.

           data-point #41  "date of last cyber audit"
                  ONE register entry
                    ↑              ↑
       [QSB] rule ≤180d      [non-QSB] rule ≤90d

Ask what goes on the intake form:
   "When did you last complete your cyber security audit?"
   → ONE question, asked of both, identical words.
     What differs is the pass mark — which lives on the RULE.

Audience separates RULES. It does not separate FACTS.
  • Definitions resolve first, whatever the document order — otherwise a rule using net_worth creates it as an ordinary fact, and the form asks the broker for a number that should have been computed.
  • Sequential by design. A fact created by clause 1.1 must be visible to clause 1.4. Run it in parallel and both look into an empty register and both create it.
  • Measured: 2,228 tokens on the master circular → 1,960 created, 268 reused, 311 judged. The false-merge guard fired for real — one token name appearing across 4 different topics was kept as six separate facts rather than merged on a matching name.
Where it breaks

Three risks that mock mode structurally cannot show, because its embeddings are random and its judge is instant local code:

  • Judge-call volume is unknown. All 311 calls came from the tripwire; the vector band never fires under mock. In production it could be 5% or 30% of tokens — the difference between ~100k and ~700k AI calls across a corpus.
  • Throughput. 2,228 tokens resolve in under a second today because there's no real AI call in the loop. Add a ~1s judge call to a sequential loop and a bulk load becomes days. Likely fix: resolve the deterministic ones first, batch the judge cases.
  • Cold-start naming is a build gap, not a test gap. Today's greedy path lets whichever circular is processed first name everything — aud_dt from 2019 beating last_audit_date used 400 times. Bulk load needs to cluster all mentions first and pick names by frequency.
14Canonical rewrite & fingerprintspartly built · has a bug

Give every rule a fixed identity — so we recognise it again when it changes.

IN rules with an audience and registry ids→OUT rules with two hashes
The idea

A master circular reissued each year repeats hundreds of rules word for word. An amendment changes one number in one of them. Compare the text and everything looks different every year. So each rule gets two hashes: one for "is this the same duty?", one for "has anything changed?" 

TWO HASHES

IDENTITY   audience  +  data-points  +  the SHAPE of the test   values removed
FULL       identity  +  the values                              everything


WHICH GIVES A THREE-WAY VERDICT

  identity      full        meaning
  ────────────────────────────────────────────────────────────────
  match         match       RESTATEMENT  master circular repeating a rule
  match         differs     AMENDMENT    same duty, the value moved
  no match      —           NEW RULE

The middle row is the entire point.
audit interval ≤ 180 and ≤ 90 must collide on identity —
that collision IS the detection.

Why the hash is built on a tree, not on text

The AI rephrases the same duty between circulars.
Every variance would manufacture a phantom new rule:

   days_between(a, b) <= 180     →  hash X
   180 >= days_between(a, b)     →  hash Y     same duty, different hash
   x AND y                       →  hash P
   y AND x                       →  hash Q     same duty, different hash

So the expression is parsed into a tree, then canonicalised:

   1  comparisons face one way    180 >= x   →   x <= 180
   2  commutative operands sorted y AND x    →   x AND y
   3  structure replaces punctuation — brackets stop existing
   4  serialise deterministically  →  hash THAT

The parser already exists — ast_parse.py builds this tree today
and then throws it away, returning only flat lists.

⚠ The bug in what's built

The code hashes the expression only. The audience never enters it.

  QSB       days_between(...) <= 180   → masked →  #4471<=NUM  →  abc123
  Non-QSB   days_between(...) <= 90    → masked →  #4471<=NUM  →  abc123
                                                                  ^^^^^^
                                                            THE SAME HASH

So the non-QSB rule files as an amendment of the QSB rule.
180 is superseded by 90. Two coexisting duties collapse into one
wrong one — no error, no flag, a quietly incorrect rulebook.

Fix: put audience_id into the identity hash. The smallest edit
in the step, and the one that must land before any bulk load.

The decision: audience by id, not by shape

A threshold change reads as…The risk
by shape
[clients] > NUM		5,000 → 10,000 keeps identity → clean amendment=='stock_broker' and =='mutual_fund' both mask to [category]==STR — a brokers' duty and a mutual-funds' duty become the same rule
by id ✓
audience #7		mints a new audience → files as a new rule, old one orphaneda duplicate sits in the review queue
 
WHY — the two errors are not symmetric:

   a false AMENDMENT   overwrites a live obligation, invisibly
   a false NEW RULE    leaves a duplicate where a human sees it

   When you are going to be wrong, be wrong LOUDLY.

By-shape reintroduces the exact disease the audience was added to cure —
silent cross-population merging — just at the category level.
  • Names never enter the hash — only ids. [Cyber.last_audit_date] → #4471, so topic spelling, the AI's naming whim and any later cosmetic rename are all irrelevant to identity.
  • Hashes stay recomputable. Identity is built from registry ids, so Step 13's cold-start clustering invalidates every hash in the database the day it merges attributes. Each rule stores its inputs — audience id, sorted attribute ids, canonical tree — making a registry migration a re-derivation rather than a rebuild.
  • Three changes to build it: return the tree from the parser · add the canonicaliser · put the audience in the hash. The funnel around it already works.
Where it breaks
  • Structural amendments are invisible to the hash. When an amendment adds a condition — interval <= 90 becoming interval <= 90 AND scope includes cloud — the data-point set changed, so identity misses and it files as new. This is common. Which is why the fingerprint is one lane of three: Step 15 also matches on citations (regulators usually say "this modifies para 9.5" outright) and on fuzzy same-audience overlap. Overselling the hash as a complete amendment detector is the mistake to avoid.
  • Operator flips file as new. "at least 180 days" → "at most 180 days" changes the shape. Rare, lands in review, acceptable.
  • Attestable rules have nothing to parse. Much of SEBI's text is "shall maintain adequate systems and procedures" — no operators, no data-points, no literals. Fallback identity: audience + attribute ids + a hash of the normalised sentence. Genuinely weaker, and there's no way around it — prose cannot be diffed structurally. The alternative isn't a better hash; it's a human.
15Filingdesigned

Where the rule finally meets the graph — new, repeated, changed, or withdrawn.

IN fingerprinted rules + the circular's dates→OUT an event log the graph is replayed from
The idea

Everything before this turns prose into a well-formed rule. This is the step all of it exists to reach. The hashes from Step 14 are computed today but nothing reads them — every rule inserts as new. Step 15 is the missing reader. 

FIVE VERDICTS

  identity   full     verdict
  ──────────────────────────────────────────────────────────────────
  ✓          ✓        RESTATEMENT  nothing changes; add a source span
                                   the most common outcome at scale
  ✓          ✗        AMENDMENT    same duty, value moved → version it
  no match   —        NEW RULE     insert, version 1, ACTIVE
  — no incoming rule at all —  REPEAL       an existing rule goes SUPERSEDED
  partial / multiple  AMBIGUOUS    review queue, nothing committed

REPEAL is the one that's easy to design past.
"Para 9.5 stands withdrawn" produces no rule to match — there is
nothing to fingerprint. Only the citation lane can reach it.

Three lanes, not one

LANE 1 · FINGERPRINT   exact identity_hash lookup
                        deterministic · free · catches VALUE changes
                        blind to everything else

LANE 2 · CITATION      the circular says so, in words:
                        "this partially modifies para 9.5 of
                         SEBI/HO/MIRSD/2023/45"
                        citation → document → clauses → obligations
                        the ONLY lane that sees structural
                        amendments and repeals

LANE 3 · FUZZY         same audience + overlapping data-points
                        + similar meaning
                        → produces CANDIDATES, never decisions

When lane 1 and lane 2 disagree, LANE 2 WINS.
The hash is an inference. The citation is a fact.

⚠ The ordering problem

Amendments only mean anything in effective-date order.
A bulk load arrives in whatever order the download gave you:

   ingest the 2026 amendment first  →  no match     →  files as NEW
   ingest the 2023 original second  →  identity ✓   →  files as an
                                       AMENDMENT moving 90 back to 180

   The graph says 180. SEBI says 90.
   No error. Nothing looks wrong.

Sorting the corpus by date fixes the bulk load and fails in the steady
state — circulars apply retroactively, so one arriving in March can be
effective from January, after statuses were already computed.
FROZEN: EVENT REPLAY

Filing does not mutate the graph. It appends an assertion:

        document D asserts rule R, effective E, verdict V

The live graph is a PROJECTION — replay the log in effective-date
order. A late retroactive circular inserts an event and replays
from its date.

Not new architecture — Layer C's rule applied one level up.
The graph is recomputed, never edited.

It also buys the otherwise-unbuildable question:
   "what did we believe on 12 March?"  →  replay to that date.
An audit pack that can't reconstruct a past belief isn't an audit pack.

Frozen: amendments are staged, never auto-applied

   restatement  →  AUTO      nothing changes; provenance only
   new rule     →  AUTO      inserted ACTIVE; flips nobody
   amendment    →  STAGED    new version written PROPOSED
                             old version stays ACTIVE until approved

The reason is not caution — the approval step IS the product.

An amendment is the only verdict that can flip a firm from compliant
to breaching. Auto-applying it deletes the exact moment the whole
amendment console exists to show:

     SEBI issued this → here is precisely which firms change → approve
  • Identity matching more than one ACTIVE rule never auto-files. Trivial shapes like x == true are low-entropy and collide across unrelated duties. A multi-match is evidence the hash isn't discriminating — not evidence of an amendment.
  • Schema work gates this and Step 14. obligations.audienceId does not exist, so Step 14's frozen decision can't be built. Plus hashInputs, the rule_assertions event log, and unresolved_citations. obligation_versions already has the right shape.
Where it breaks
  • Citations into documents we don't have. A 2024 circular amending a 2019 one that was never ingested. Store the citation unresolved, resolve it retroactively when that document lands — Step 16's machinery, so a dependency rather than a new problem.
  • Silent duplicates. A master circular restates a rule, but Step 13 resolved one token to a different data-point this time, so the shape differs and it files as new. Two copies of one duty, both ACTIVE, no error raised. Only lane 3 finds it, and only if someone reads the queue. No clean fix — it's the standing cost of a pipeline with AI upstream of a hash.
  • Vague repeals. "All previous instructions on this subject stand withdrawn" cites nothing resolvable. Review queue, and realistically a human has to read the circular.
16Link resolutiondesigned

Turn "para 9.5.3.1" into an actual edge between two rules.

IN citation strings parked at Step 9→OUT a linked graph
Why it waits until now

A link joins two rules — and rules don't have ids until Step 15 files them. Detection had to happen early (Step 9 needed it to build windows); resolution could only happen here.

Most citations are already gone

Four of the five citation kinds are consumed before Step 16:

  "shall have the meaning assigned in para X"   Step 9   inlined
  "nothing in para X shall apply to…"           Step 12  → modifier
  "this partially modifies para 9.5"            Step 15  → amends
  "para 9.5 stands withdrawn"                   Step 15  → supersedes
  "where unable to comply with para X…"         nobody yet  → depends_on

So Step 16 is four narrow jobs, not "resolve all citations":

  1  depends_on      conditional triggers — the only kind left
  2  shared_evidence not citation-derived at all — computed from overlap
  3  the retry sweep citations parked waiting for their document
  4  split_of        one clause yielding several rules

A citation names a CLAUSE. An edge joins RULES.

   clause 9.5.3.2 cites "para 9.5.3.1"
            ↓
   but 9.5.3.1 produced THREE rules — a clause routinely yields several
            ↓
   which one does the exception-report duty depend on?

The answer depends on the edge type:

  depends_on            FAN OUT to every rule from that clause
                        over-linking is recoverable — evaluation walks
                        it and finds nothing wrong

  amends / supersedes   MUST BE PRECISE
                        amending three rules when SEBI meant one
                        corrupts the graph → ambiguous goes to review

Fan out where being wrong is loud. Stop where it's silent.
THE RETRY SWEEP — event replay pays off a second time

A 2024 circular cites a 2019 one we haven't ingested. Step 15 parks it.
When 2019 lands, a sweep asks "who was waiting for me?"

But that can change a past filing verdict — a rule filed as NEW in
2024 turns out to have amended a 2019 rule all along.

   without an event log   history must be rewritten in place
   with one (Step 15a)    append a correction event, replay

This wasn't why event replay was chosen — which is usually the sign
a structural decision was right.
  • ⚠ Schema gap — an edge cannot be explained. edges holds only fromId · toId · type · createdAt. No citing clause, no span, no confidence. An auditor can't be shown why the graph believes A depends on B.
Where it breaks
  • Cycles. A → B → C → A. Step 24 walks these during evaluation, so a cycle is an infinite loop in the product's hot path. Detection must happen at insert time — caught at evaluation it's a production hang, and the firm whose status triggered it is the one who sees it.
  • Bare numbers. clause_no isn't a key — "1" appears 153× in CSCRF. Resolve within the citing clause's own subtree first, then document-wide, then review.
  • Citations outside the corpus. "Regulation 9(2) of SEBI (Stock Brokers) Regulations, 1992" — a document class we may never ingest. Store as an external reference; no edge, still shown as provenance.
  • Annexures and forms. "as per Annexure A" targets a template, not a rule.
17Consistency checksdesigned

Ask the question nothing before it could — does the graph agree with itself?

IN the whole projected graph→OUT a triaged findings list
The idea

This is the capability nothing on the market has — and it's available only because Steps 10, 13 and 15 produced machine-readable audiences, a canonical data-point registry, and one graph holding both. Without all three, "do these two rules conflict?" is unanswerable. 

THE HEADLINE CHECK — CONTRADICTION

  Rule A   audience = QSB             cyber_audit_interval <= 180
  Rule B   audience = stock brokers   cyber_audit_interval >= 365

  QSB ⊂ stock broker     →  the audiences OVERLAP
  same data-point #4471  →  the ranges cannot both hold
                         →  no QSB can comply with both

Two machines do this, and both already exist:
   audience overlap    → a lattice-implication check  (Step 10)
   expression conflict → interval arithmetic on one attribute id
FOUR FAMILIES OF FINDING

  1  CONTRADICTION   two ACTIVE rules no single firm can satisfy
  2  DEAD RULE       unsatisfiable audience · missing category ·
                     SUPERSEDED with no successor
  3  REDUNDANCY      two ACTIVE rules sharing an identity_hash
                     ← exactly the silent duplicate Step 15 couldn't catch
  4  INTEGRITY       missing source spans (the audit pack breaks) ·
                     edges into superseded rules · cycles ·
                     registry entries no rule references

Scoped deliberately: single-attribute interval conflicts

General satisfiability is an SMT problem — slow, and it produces
findings nobody can act on. It's also unnecessary:

Real regulatory contradictions are almost always two different
numbers for the same duty — two deadlines, two thresholds,
two frequencies.

   IN SCOPE       same attribute id, operators with disjoint ranges
   OUT OF SCOPE   multi-variable satisfiability, cross-attribute maths

COST. Pairwise is O(n²) — 2.5 billion pairs at 50,000 obligations.
But two rules can only contradict if they share an attribute, so
bucket by attribute id first. Most attributes appear in a handful of
rules → the work collapses to near-linear.

⚠ A contradiction is usually OUR bug, not SEBI's

Most findings will trace back to:

   a mis-resolved audience                 Step 10
   two facts wrongly merged                Step 13
   a modifier applied to the wrong target  Step 12
   an unnormalised unit                    Step 11

Not to SEBI issuing conflicting requirements.

So Step 17 isn't only a feature — it's the pipeline's regression test.
It's the ONLY check that can catch a Step 10 or Step 13 error after
the fact, because it compares rules against each other rather than
against the document they came from.

Which is why it's worth building EARLY, not last.
Run it on a two-document corpus and it audits every step before it.
Where it breaks
  • One bad audience floods the queue. If Step 10 wrongly merged two audiences, every rule pair beneath them looks contradictory — hundreds of findings, one cause. Cluster by probable root cause and show the cause once. A findings list that can't be triaged won't be read.
  • Unit mismatches look like contradictions. <= 180 days vs <= 6 months is the same rule twice. Step 11 normalises time to days — but any unnormalised unit produces a phantom, and the check can't tell.
  • Conditional rules. Two rules that look contradictory but are gated by preconditions that never co-occur. Checked at lower confidence and reported separately.
  • Sometimes the regulation really does contradict itself. A later circular can conflict with an earlier one without formally amending it. The system can't resolve that — only surface it. Which is arguably the most valuable thing it produces, and the one output no existing compliance tool can generate at all.

Five principles that recur everywhere

PrincipleWhat it means in practice
Embeddings retrieve.
Symbols decide.		 Similarity narrows the candidates; something exact and checkable makes the call. Every product that lets a similarity score decide stays a demo.
The AI is never the
first responder or the last word.		 Cheap deterministic check → tripwire → targeted adjudication with a specific complaint → verify the answer with the same check. Used by the attribute funnel, the numbering audit and number fidelity.
Fail toward visible. Every unresolved case becomes a question in a queue, never a silent decision. A regulator accepts "16 items flagged for review"; never "an obligation was quietly dropped".
Buy the expensive layer once. AI output is cached forever and keyed by content. The clever logic on top is free to re-run — so it can be improved fifty times a day without re-paying for extraction.
Never show a number
that came from a model.		 Review screens state applicability in plain English, generated from the rule itself. A fabricated firm count sitting in a compliance screen looks authoritative and is worse than no number.
